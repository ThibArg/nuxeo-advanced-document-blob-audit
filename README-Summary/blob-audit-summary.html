nuxeo-advanced-document-blob-audit

In a nutshell
  • When a document gets a new version and the bytes of a watched file have really changed, the plugin compares that file with the one in the previous version.
  • Now (inside the user's transaction): a small audit entry blobContentModified, holding no business content, only the xpath, the file names and a correlation id.
  • Later (background job): both files are read, an extractor chosen by MIME type turns each into comparable units, one generic engine diffs them, and the result is stored in a BlobDiff document.
  • Every BlobDiff lives in a locked-down folder, /change-diff/yyyy/MM/dd, readable only by the auditors group (default administrators). Nothing is ever written on the source document.

1.The big picture

synchronous, inside the user's transaction asynchronous, after commit audit log stored result
One check-in, one decision per watched file property, two outputs: a lightweight audit entry now, a full diff document later.

2.What triggers it: versions, not saves

The trigger

Two events of a check-in, both fired on the live document:

  1. aboutToCheckIn: which version is the last one right now? → v1.0
  2. documentCheckedIn: which version was just created (checkedInVersionRef)? → v1.1

The pair is exact, nothing is guessed from version labels. Any way of creating a version counts: manual, automatic versioning policy, restore, publish…

Ignored (no audit entry, no diff)

  • A plain save that creates no version
  • The first version (nothing to compare with)
  • A file added or removed: only a replaced file is audited
  • Same digest on both sides, even if renamed
  • Document types / xpaths not configured
  • Everything, when the feature is disabled (the default)
  • Code muted on purpose: context flag disableBlobDiffListener or runDisabled(...) (imports, migrations)

3.The synchronous decision (fast, no content read)

For each watched xpath, BlobDiffTrigger decides from metadata only. The order matters: the digest check comes before any skip is reported, so an over-sized file whose bytes did not move stays silent.

A version that replaced two watched files produces two independent decisions: up to two entries and two BlobDiffs.

4.The audit entry

A regular Nuxeo audit entry, category document, so it shows up in the document's History tab. The plugin contributes the audit route that persists the event and adds it to the eventTypes vocabulary.

eventId     blobContentModified
docUUID     <id of the live document>
principal   jdoe                         (the user who created the version)
extended    xpath             = file:content
            oldFilename       = budget-v1.xlsx
            newFilename       = budget-v2.xlsx
            diffCorrelationId = 7f3c…    ← the BlobDiff will carry the same id
            (or skipReason = skipped…, never both)

The correlation id is generated before the BlobDiff exists: it is a "promise" id that the background job stamps on the document it creates.

5.The background job (BlobDiffWork)

① Short read (transaction)

Already a BlobDiff with this correlation id? → stop.
Source deleted? → error BlobDiff.
Re-check the configuration. Load both files by storage key.
→

② Heavy part (NO transaction)

Materialise each file once to a local temp file, extract (§6), diff (§7).
No transaction is open, so no transaction timeout on big files.
→

③ Write (new transaction)

Check "already done?" again, create the dated folders if needed, then the BlobDiff, as system.
  • Frozen pair. The storage keys (provider + key) of both files are captured at check-in: a later edit cannot turn v1.0 → v1.1 into v1.0 → "whatever is current".
  • Idempotent. Deterministic work id (a pair is never queued twice) and correlation-id check (a job that runs twice never creates two BlobDiffs). Transient failures are retried twice.
  • Isolated. Dedicated blobDiff queue, 2 threads: a burst of large Office/PDF check-ins cannot starve other work.
  • Always leaves a trace. Once the audit entry has a correlation id, the job ends with a BlobDiff: ok, skipped… (e.g. maxBlobSize lowered meanwhile) or error (retryable).

6.Choosing the extractor: an ordered MIME-type ladder

No scoring, no lookup table: extractors are sorted by order and the first one that accepts the MIME type wins (lower-cased, ; charset=… removed). text/* is the only wildcard; everything else is an exact match.

Walked top to bottom; nothing below the first match is consulted.
Extension point. Adding a format = contributing one extractor to the extractors point, with its MIME types and an order (lower to pre-empt a built-in, higher to catch what the built-ins miss). The diff engine does not change. Beware: a contribution at order 5 accepting * would shadow everything.

Optional: the image inventory (imageAnalysisLevel = 1)

Text extraction ignores pictures. At level 1 (default 0, off), a second ladder (the imageExtractors point: imageWord, imageSpreadsheet, imagePresentation, imagePdf, all backed by ImageInventoryExtractor) lists every placed image with a stable key and its SHA-256, e.g. excel:image:Budget:B4:F18, powerpoint:slide:3:image:image1.png, pdf:page:2:image:1. The result is a keyed diff appended under a # Images heading. Images are compared by hash, not visually; PDF images are never decoded (raw stream hashed — protects against compression bombs), so a re-compressed identical-looking picture is reported as changed.

7.The diff engine: one TextDiffer for every format

Every extractor produces a DiffableContent: a list of ContentLine(key, value). Whether units carry a key decides the comparison mode. No external diff library.

Both sides must be keyed. An .xlsx replaced by a .csv is compared positionally — correct, rarely meaningful.
  • Everything is bounded: file size, units extracted, length of a unit, reported entries, diff size, bytes read per image. Past a bound, the diff is flagged truncated; the counters stay exact.
  • The result: counters (added / removed / changed), an English summary such as "1 modification, 1 addition" (the UI localises from the counters) and the diff text, rendered in colour in the UI.

8.The BlobDiff document and how everything is linked

Document → diffs: query BlobDiff where sourceId = A. Audit entry → diff: join diffCorrelationId = bdiff:correlationId (no clickable link in History).

What it contains (bdiff:*)

What / wheresourceId, sourceRepository, xpath
Versionsprevious/new VersionId & Label, versionSeriesId
Who / whenuser, date (= check-in time), correlationId
Filesold/new filename, digest, MIME type, length, storage key (used by Retry)
Resultstatus, summary, added, removed, changed, truncated
Diffbdiff:diff, a blob <name>.diff.txt

Stored as a blob (not a DB field), type flagged NotFulltextIndexable, hidden in navigation and collections.

Where it lives

/change-diff        hidden · local ACL: auditorsGroup →
 │                   Read, Remove, RemoveChildren;
 │                   inheritance BLOCKED
 └── 2026/10/24      dated folders (UTC), inherit the ACL
      └── <sourceId>-<time>-<correlationId>
  • Root created at every startup (even when disabled); ACL checked and repaired.
  • Statuses: ok, error (retryable), skippedTooLarge, skippedUnsupportedType.

Confidentiality. A BlobDiff holds business content copied out of the source and protected by a different ACL: an auditor can read the diff of a document they cannot open. By design — choose the group deliberately (org.nuxeo.web.ui.blobaudit.auditorsGroup, shared by server and Web UI).

The guards

  • BlobDiffLocationListener: a BlobDiff exists only under /change-diff and cannot leave it (no forged diffs elsewhere).
  • Server-side checkAuditor on every operation; hiding things in the UI is only cosmetic.
  • Retry accepts only an error BlobDiff under /change-diff, so a forged document cannot make the server read arbitrary blobs.
  • Purge runs as the caller (ACL applies), deletes only BlobDiff whatever the query, is not exposed through the generic bulk REST endpoint, one at a time.

10.What auditors get in Web UI

① Drawer: "Content changes audit"

Search page: date range, source, user, "truncated only"; facets on status, format, xpath, user. Needs Elasticsearch/OpenSearch.

② Document tab: "Content changes"

On documents with the file or files schema: list of their diffs (date, v1.0 → v1.1, user, xpath, summary, status), plus "open all" to the pre-filtered search.

③ BlobDiff page

Metadata, the colour-coded diff (green +, red −, orange ~), and Download, Retry (error only), Delete permanently.

④ Housekeeping

Purge older than a date (optionally by status), async bulk action with progress/abort, then empty folders cleaned. No automatic retention.

Operations: BlobDiff.Retry, .Delete, .Purge, .PurgeStatus, .PurgeAbort, .CleanEmptyFolders — auditors only.

13.Good to know

  • No version, no audit. A file replaced without versioning shows up at the next version, compared with the previous one.
  • Text only. Formatting is not diffed; a scanned PDF without OCR gives ok with an empty diff.
  • Excel is structurally sensitive. Inserting a row shifts every cell below; renaming a sheet = all cells removed then added.
  • MIME matching is exact. application/x-yaml and text/yaml match, application/yaml does not.
  • Image inventory quirks. The image reader is chosen from the new version's MIME type. Macro-enabled .pptm/.ppsm and a PDF MIME type with parameters yield an empty image inventory silently (text is unaffected).
  • Imports and migrations: mute the listener, or every re-versioned document produces a diff.
  • Retry works only while the old binaries are still in the blob store (the binary GC can remove them).
